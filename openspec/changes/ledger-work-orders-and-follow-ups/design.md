# Design

## Context

See `proposal.md` for motivation and `specs/` for observable behavior. 当前欠费模块直接查询每个统计月份的当前快照；专线续签模块已有按“统计日期 + 成员服务号码”唯一的工单及状态历史，详情 API 返回状态历史，状态更新在事务中锁定工单。归属信息保存在快照记录中，客户经理权限依据当前有效归属计算。

本变更让欠费工单沿用独立快照的存储和权限模型，并为两种工单补充可追溯的跟进说明。欠费数据与专线数据仍保持独立，不建立跨表业务关联。

## Goals / Non-Goals

**Goals:**

- 欠费记录按“统计月份 + 账户 ID”建立互不继承状态的工单，并能复用同月修正版中的原工单。
- 两种工单都能分别查询状态变化和跟进说明，并在详情中合并为稳定排序的时间线。
- 状态更新与跟进说明追加遵循权限校验、工单行锁和事务一致性；最后处理字段反映最近一次实际处理。
- 欠费工单报表与欠费原始明细、专线续签报表保持清晰边界。

**Non-Goals:**

- 不改变 Excel 欠费和专线快照的字段映射、必填校验、文件保存和导入预览流程。
- 不把欠费工单与专线续签工单合并，也不增加风险等级、催缴策略、自动任务或通知。
- 不把跟进说明加入任何工单报表或原始 Excel 导出。
- 不引入工单之间转派、协作评论、附件或跟进说明修改/删除功能；已追加记录保持只读。

## Decisions

### 1. 为欠费工单建立独立的月度业务键

新增 `arrears_work_order`，唯一键为 `(statistics_key, account_id)`，并保存当前快照引用、三种状态、最后处理人和时间。`statistics_key` 使用导入批次的统计月份，账户 ID 保留来源数据值作为稳定业务标识。不同月份的同一账户始终对应不同工单。

**替代方案：**按账户跨月份复用一张工单。该方式会把不同月份的处理结果和统计口径混在一起，与按月查看和导出的需求冲突，因此不采用。

### 2. 状态历史和跟进说明按工单类型分别持久化

欠费工单使用独立的状态历史表和跟进说明表；专线工单继续使用现有状态历史表，并新增专线跟进说明表。两种跟进表分别通过外键引用所属工单，避免以 `source_type + polymorphic_id` 实现而失去数据库外键完整性。跟进内容使用文本字段，保存填写人和数据库生成的创建时间。

**替代方案：**使用一张多态工单活动表。它减少表数量，但无法以普通外键确保记录引用的工单真实存在，且查询必须额外按类型分支；在只有两种明确工单类型时，分表更容易维护和约束。

### 3. 一个事务处理状态变化、跟进说明和最后处理信息

状态操作在锁定工单后验证当前归属与管理员权限，再执行可选状态变化和可选说明追加。输入说明先去除首尾空白；空白内容视为未填写。说明仅在操作完成后的目标状态为“跟进中”时接受。状态实际变化时写一条状态历史；非空说明写一条独立跟进记录。任一写入发生时，同一事务更新最后处理人和时间。状态未变化且没有说明时按无操作处理，不改变最后处理字段。

**替代方案：**把说明作为状态历史的一部分。说明可能在状态不变时多次追加，这样会伪造状态变化；单独持久化可以准确表达两种事件。

### 4. 详情时间线由两类记录合并形成

详情 API 分别读取工单状态历史和跟进记录，将两者映射为统一的时间线事件：类型、前后状态（仅状态事件）、说明（仅跟进事件）、操作人、发生时间和来源记录编号。按发生时间升序排列；相同时间按事件类型和来源记录编号稳定排序。前端按事件类型显示状态转换或说明内容。现有专线状态历史保持可追溯，并作为时间线中的一种事件呈现。

**替代方案：**把状态历史和跟进说明放在详情的两个独立表格。用户需要交替比对才能还原处理经过，不能清楚看到说明与状态改变的先后，因此采用统一时间线。

### 5. 修正版通过自然键复用工单，只更新当前快照引用

欠费导入确认在同一事务内按 `(statistics_key, account_id)` 锁定或创建工单，并把当前快照引用切换到新记录。专线现有按 `(statistics_key, member_service_number)` 复用方式扩展跟进记录保留。修正版新增键创建待处理工单；旧版本中存在但新版本移除的键不出现在当前查询，因为列表通过 `excel_current_version` 连接当前批次；工单与两种历史表不删除。若键随后在同月/同日期修正版中重新出现，则更新快照引用并继续使用原工单。

**替代方案：**每次修正版都新建工单。该方案会丢失持续处理中状态和历史之间的连续性，因此不采用。

### 6. 统一权限依据，但保持两种数据域独立

工单详情、状态/说明写入和时间线读取均通过当前快照的 `effective_manager_user_id` 校验；未分配工单仅管理员可访问。历史统计月份继续按照该月份当前生效快照上的有效归属处理，不因月份较旧而只读。欠费工单导出只允许管理员，使用统计月份范围和工单状态等欠费筛选条件，不应用分页；跟进说明及状态历史不进入导出。

**替代方案：**在工单表复制客户经理归属并将其作为权限真相。归属会由管理员维护且可能修正，复制字段容易过期；继续以当前快照归属作为唯一权限来源。

### 7. 追加式数据库迁移和幂等回填

新增迁移创建欠费工单及其历史表，并为专线工单创建跟进表。迁移对所有已有月份的当前欠费版本幂等回填“待处理”工单，不生成虚构状态历史或跟进说明；已有专线工单不重置状态或最后处理信息。迁移只增加表和索引，不删除或改写 Excel 快照与导入批次。

**替代方案：**依赖每次应用启动自动执行业务迁移。项目当前通过显式 SQL 迁移管理数据库结构，继续沿用该做法更便于备份、检查和控制部署顺序。

## Risks / Trade-offs

- [历史时间线记录量会随工单使用增长] → 当前详情模式已读取完整专线状态历史；首版沿用详情按工单加载，给时间和编号建立复合索引，并验证稳定排序。若实际记录规模增长，再单独增加时间线分页。
- [并发导入可能同时创建同一月度欠费工单] → 在导入事务内锁定月份当前版本，配合自然键唯一索引；唯一键冲突作为并发保护并验证批次状态一致。
- [跟进说明可能包含不适合导出的内部信息] → 仅授权用户在详情时间线查看，导出服务使用固定字段映射，明确排除说明与状态历史。
- [客户经理归属在历史月份可能被维护变更] → 与当前业务权限规则保持一致，所有工单查询和修改即时依据对应快照上的当前有效归属执行。

## Migration Plan

1. 备份当前业务数据库，并在隔离测试库执行新增 SQL 迁移及回填。
2. 验证表约束、外键、索引，确认回填工单数量与所有月份当前欠费快照数量一致且重复运行不增加记录。
3. 部署兼容迁移后表结构的后端和前端；原始快照表与既有专线状态数据保持不变。
4. 验证管理员与客户经理权限、当前及历史月份处理、修正版保留、状态历史、跟进时间线和两种导出。
5. 如需回滚应用，先停止接受工单写入，再回退应用版本；新增工单和跟进表不自动删除，以保留处理数据。数据库回滚需单独制定并经管理员确认，不通过破坏性逆向迁移执行。
