# Design

## Context

专线数据以 `line_expiry_snapshot` 保存每个导入批次的不可变快照，`excel_current_version` 指向每个统计日期的当前批次；同一成员服务号码可以在多个统计日期出现。当前专线查询已经按当前版本和有效归属控制访问，但没有承载人工续签处理信息。新能力必须与 Excel 原始字段和归属信息分离，不能让修正版覆盖人工处理记录。

## Goals / Non-Goals

**Goals:**

- 为统计日期和成员服务号码建立稳定的专线续签工单身份。
- 在修正版切换当前快照时复用既有工单，并为新增专线初始化工单。
- 提供任意状态切换、状态历史、权限校验、页面状态筛选和管理员固定字段导出。
- 保留现有专线明细导出与欠费台账的独立性。

**Non-Goals:**

- 不为欠费记录创建工单。
- 不根据计费截止日期、剩余天数或风险规则自动改变工单状态。
- 不增加最后处理时间范围筛选、通知、审批流或外部 CRM/工单系统同步。
- 不把处理状态写回 Excel 原始字段或修改原始工作簿。

## Decisions

### 1. 独立工单表，以统计日期和成员服务号码作为自然唯一键

新增 `line_renewal_work_order`，保存统计日期、成员服务号码、当前状态、最后处理人、最后处理时间和当前快照记录引用；对 `(statistics_key, member_service_number)` 建唯一约束。状态使用受约束的中文枚举值：`待处理`、`跟进中`、`已续签`、`不续签`。

新增 `line_renewal_status_history`，保存工单、原状态、新状态、操作人和操作时间。状态相同时直接返回成功或当前结果，不写历史。使用独立表而不是复用旧 `task` 表，因为旧任务关联旧版 `customer`/`business_service`，无法稳定表达独立 Excel 快照的月份身份。

### 2. 工单与当前快照关联，历史快照不携带人工状态

确认专线批次时，在同一事务中根据统计日期和成员服务号码查找工单：存在则更新其当前快照记录引用，不修改处理字段；不存在则创建“待处理”工单。当前版本查询通过 `excel_current_version` 取得的专线快照连接工单，因此修正版删除的行自然从当前页面消失，工单和历史仍保留。若之后同一自然键再次出现，重新关联既有工单并恢复其历史状态。

导入确认前先按批次编号升序锁定同一来源和统计日期的所有候选批次，再锁定当前待确认批次；避免两个修正版确认事务先各自锁住批次、再反向等待对方造成死锁。随后对工单自然键使用数据库唯一约束和行级锁，避免并发确认创建重复工单。续签工单写入失败时，快照确认和工单写入整体回滚。

### 3. 状态更新使用服务端权限和乐观的当前状态检查

新增专线工单查询、详情和状态更新接口。客户经理的读写范围由当前 `excel_snapshot_record.effective_manager_user_id` 决定；管理员绕过归属限制。状态更新请求必须包含目标状态，服务端校验四个允许值，并在事务中锁定工单、重新确认当前归属和当前状态，然后更新工单及追加历史。任意状态可互相切换；重复提交相同状态不更新最后处理信息，也不产生历史。

### 4. 专线页面复用查询条件，工单报表独立于原始明细导出

专线主列表在已有日期范围、集团、产品、客户经理和剩余天数筛选基础上增加状态参数，响应增加工单当前状态、最后处理人和最后处理时间。详情抽屉展示并允许有权限的用户修改状态，同时显示状态历史。

保留现有专线原始明细导出，不加入系统派生的剩余天数。新增仅管理员可用的续签工单报表接口，复用专线查询的日期范围、集团、产品、客户经理和状态条件，但固定输出统计日期、集团编码、集团名称、产品编码、产品名称、成员服务号码、Excel 原始客户经理、当前有效客户经理、计费截止日期、状态、最后处理人、最后处理时间，且不受分页影响。

### 5. 时间和修正版语义

统计日期只表示工单所属快照日期；最后处理时间使用服务端数据库时间，表示人工状态最后一次实际变化时间。初始工单不写最后处理人和最后处理时间。修正版不继承其他统计日期的工单状态，也不因当前日期或剩余天数自动改状态。

## Risks / Trade-offs

- **[修正版与人工记录关联错误]** -> 使用规范化统计日期和成员服务号码的二进制/大小写敏感唯一键，并在导入确认测试新增、修改、删除、重新出现四种情况。
- **[并发状态更新覆盖]** -> 在事务中锁定工单并以当前状态为依据写历史；状态历史按数据库时间和自增编号排序。
- **[当前版本删除后工单不可见]** -> 当前列表只展示当前快照，管理员通过批次/审计查询保留历史工单；再次导入同一自然键时重新关联。
- **[旧任务模块语义混用]** -> 不复用旧 `task` API 或旧业务外键，明确新增接口和表的专线快照边界。
- **[导出字段与原始明细导出混淆]** -> 使用单独的续签工单导出入口和固定表头，并在权限测试中拒绝客户经理访问管理员报表。

## Migration Plan

1. 发布新增工单表和历史表的向前兼容数据库迁移，不修改旧表和既有快照。
2. 部署后对当前已有的专线当前版本执行一次幂等初始化，为每个 `(统计日期, 成员服务号码)` 创建“待处理”工单；初始化不生成虚构的处理历史。
3. 启用专线导入确认、查询、状态更新和导出接口，先用独立测试数据库验证权限与修正版场景。
4. 若需回滚，停止工单写入口并回退页面/API版本；保留新增表和人工历史，避免删除用户已提交的处理记录。重新部署时通过唯一键继续复用。
