## 3. 表结构和关联

### 3.1 核心主表

| 表 | 主键 | 业务唯一约束 | 关键索引 |
| --- | --- | --- | --- |
| app_user | id | username | username |
| customer | id | customer_code | manager_name、risk_status |
| business_service | id | customer_id + service_code | customer_id + status、manager_user_id |
| arrears_bill | id | customer_id + bill_code + billing_period | customer_id + billing_period、arrears_amount |
| contract_expiry | id | service_id + expiry_date | expiry_date + renewal_status、customer_id |
| task | id | customer_id + source_record_code | deadline、owner_name、task_status |
| follow_up | id | 无单独业务唯一约束 | task_id |

### 3.2 导入、风险和审计表

| 表 | 主键 | 关键索引或约束 |
| --- | --- | --- |
| import_batch | id | created_at |
| import_row | id | batch_id |
| exception_record | id | batch_id + status、exception_type + status |
| risk_rule | id | rule_code + version、is_enabled + effective_from |
| risk_result | id | source_record_type + source_record_id + rule_id + run_id、customer_id + status |
| risk_recalculation_run | id | status + started_at |
| operation_audit_log | id | operator_user_id + created_at、operation_type + created_at |
| user_customer_scope | id | user_id + customer_id、customer_id |

### 3.3 外键关系

1. `customer` 是客户主实体。
2. `business_service.customer_id`、`arrears_bill.customer_id`、`contract_expiry.customer_id`、`risk_result.customer_id` 和 `user_customer_scope.customer_id` 引用 `customer.id`。
3. `contract_expiry.service_id` 和 `arrears_bill.service_id` 引用 `business_service.id`。
4. `task` 通过 `customer_id`、`service_id`、`rule_id` 和来源字段关联业务、风险及任务触发来源。
5. `follow_up.task_id` 引用 `task.id`，跟进历史不能因风险重算被覆盖。
6. 导入行和异常记录通过 `import_batch`、`import_row` 保留原始追溯。
7. 风险结果通过 `risk_rule`、`risk_recalculation_run` 和可选导入批次关联计算版本与来源。
8. 审计、账号范围、规则创建人和异常处理人引用 `app_user.id`。

所有已检查外键均为 InnoDB `NO ACTION`，删除和更新不能绕过业务关联强制删除。

## 4. 迁移映射

项目当前使用 `db/migrations/V1__enterprise_arrears_schema.sql` 作为版本化、可重复执行的增量基线。当前没有启用 Flyway 自动执行，迁移由运维或开发人员显式执行并记录结果。

| 规划能力 | 当前实际表 | 当前处理 |
| --- | --- | --- |
| 用户与角色 | app_user | 已具备；保留现有账号和密码哈希 |
| 客户范围 | user_customer_scope | 已具备；唯一约束防止重复授权 |
| 客户 | customer | 已具备；customer_code 已建立唯一约束 |
| 业务服务 | business_service | 已具备；customer_id + service_code 唯一 |
| 欠费账单 | arrears_bill | 已具备；金额为 DECIMAL(18,2)，保留账期和来源批次 |
| 到期记录 | contract_expiry | 已具备；关联业务和到期日期 |
| 任务及跟进 | task、follow_up | 已具备；人工状态与风险结果分离 |
| 导入批次及行 | import_batch、import_row | 已具备；保留 SHA-256、批次统计和原始行 JSON |
| 风险规则及结果 | risk_rule、risk_result、risk_recalculation_run | 已具备；规则版本和重算运行可追溯 |
| 异常 | exception_record | 已具备；支持批次、原始行和处理结论 |
| 审计 | operation_audit_log | 已具备；不保存密码或会话令牌 |

当前结构与 V1 迁移脚本对齐，没有发现需要立即新增的表或字段。再次执行 V1 脚本后，15 张表和当前存量行数均无差异。因此本轮不新增 SQL 结构、不删除字段、不重命名字段。

## 5. 数据访问和事务边界

1. 后端使用 Spring JDBC `JdbcTemplate`，当前未引入 MyBatis、MyBatis-Plus 或 Flyway。
2. 所有带业务输入的查询和写入使用参数化 SQL；排序字段使用服务端白名单映射。
3. Excel 预检、批次确认、任务写入、风险重算和规则版本更新使用 Spring 事务边界。
4. 导入批次确认在事务内按客户、业务、账单、到期、跟进和规则顺序写入；失败时回滚正式业务写入并保留失败批次和行级错误。
5. 导入预检和确认使用数据库锁串行化重复文件和批次写入，避免并发确认产生重复记录。
6. 风险重算只更新派生风险结果，不更新人工跟进内容或任务处理历史。
7. 金额使用 `DECIMAL(18,2)`，日期使用 `DATE`，时间使用 `DATETIME`，状态字段由业务服务校验。

现有后端集成测试覆盖空值、负金额、重复键、金额计算、事务回滚、导入幂等、权限范围、风险边界和任务生命周期。

## 8. 后续建议

1. 在正式环境引入 Flyway 前，先将当前 V1 脚本登记为已执行基线，避免自动工具重复执行历史迁移。
2. 后续结构变化新增 `V2__...sql`，不得修改已执行的 V1 脚本内容。
3. 生产部署前在隔离临时库执行一次完整恢复演练，并记录恢复后的表数、行数、外键和登录验证结果。
4. 当前 `backend/src/main/resources/schema.sql` 是早期初始化草稿，不应作为当前生产数据库的结构依据；后续应明确废弃或更新其用途，避免与 `db/migrations` 产生歧义。
