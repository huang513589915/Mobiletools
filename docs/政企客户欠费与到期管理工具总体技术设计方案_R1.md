## 1. 文档目的

本文档用于说明“政企客户欠费与到期管理工具”第一阶段的总体技术方案，为平台评审、详细设计、开发实施、测试部署和后续验收提供技术依据。

本文档重点回答以下问题：

1. 系统采用什么总体架构和技术栈。
2. 前端、后端、数据库、任务调度和外部依赖如何协作。
3. 欠费、余额、到期、预警、任务和督办数据如何流转。
4. 如何保证内部敏感数据的权限、安全、审计和可追溯。
5. 哪些内容可以在第一阶段落地，哪些内容需要后续确认或扩展。

本文档不是接口详细设计、数据库物理设计或最终部署实施手册。接口字段、具体服务器规格、正式数据源和预警阈值需在技术评审及业务确认后固化。

## 2. 设计原则

### 2.1 业务原则

- 系统定位为欠费与到期风险管理工具，不替代现有计费、账务、客户关系管理或工单系统。
- 正式账务金额、业务状态和停复机状态以公司认可的正式数据源为准。
- 短信、线下表格等数据可以作为辅助来源，但不得仅凭未经核实的短信直接执行停机、扣款或账务修改。
- 系统重点解决信息汇总、风险识别、任务推动和处理闭环问题。

### 2.2 技术原则

- 第一阶段采用模块化单体架构，控制部署和运维复杂度。
- 后端独立存在，前端不得直连数据库或绕过后端权限。
- 所有导入数据先预检，再进入正式业务数据区。
- 核心数据保留来源、批次、更新时间、核查状态和处理历史。
- 预警规则可配置、可解释、可追溯，避免将规则散落在页面代码中。
- 所有关键业务操作具备审计记录。
- AI 仅提供授权范围内的只读辅助查询和摘要，不参与正式账务判断和高风险业务动作。
- 优先采用成熟、通用的认证、权限、消息、日志、文件存储和数据接入实现，后续可根据部署环境进行适配。

### 2.3 交付原则

- 先完成数据来源、业务规则、权限边界和平台能力确认，再锁定详细技术实现。
- 先建设可验证的欠费和到期管理闭环，再扩展复杂预测、自动外呼等能力。
- 每个核心模块都应具备明确的验收场景和可追溯测试记录。

## 3. 建设范围

### 3.1 第一阶段建设范围

第一阶段建议建设以下能力：

1. 欠费、余额、专线到期和客户归属数据的文件导入或接口接入。
2. 数据预检、错误明细、重复识别和异常核查。
3. 客户、业务、欠费、余额、到期和责任人的统一台账。
4. 基于规则的余额不足、欠费、停机风险和到期预警。
5. 预警转任务、任务分派、转派、跟进、催办、升级和关闭。
6. 客户经理跟进记录、缴费结果、续签结果和备注登记。
7. 后台风险监控、任务统计、异常查询和授权导出。
8. 用户、角色、数据权限、操作日志和运行异常日志。
9. 提供权限受控的辅助查询能力，AI 接入方式根据实际部署环境配置。

### 3.2 暂不纳入第一阶段

- 替代现有计费、账务、客户关系管理或工单系统。
- 自动修改账务、自动扣款或自动执行停复机。
- 仅凭短信内容自动认定欠费并直接触发业务动作。
- 面向外部客户的公开查询、自助缴费或客户门户。
- 未经安全评审确认的公网部署和外部 AI 服务接入。
- 复杂预测模型、自动外呼和自动催收话术生成。

## 4. 总体架构

### 4.1 架构分层

系统建议划分为六层：

1. **访问层**：系统用户、登录服务和 Web 前端访问入口。
2. **展示层**：React 前端应用，负责页面展示、查询条件、表单和交互。
3. **业务服务层**：Spring Boot 模块化单体后端，负责权限、台账、预警、任务和审计。
4. **数据处理层**：文件导入、接口同步、数据预检、标准化、去重和异常处理。
5. **数据存储层**：关系型数据库、内部文件存储、缓存和日志存储。
6. **平台支撑层**：认证服务、消息服务、日志监控、AI 服务和现有业务系统。

### 4.3 核心数据流

```text
数据源
  -> 接入适配器
  -> 导入批次
  -> 数据预检
  -> 标准化与客户/业务匹配
  -> 正式台账
  -> 风险规则计算
  -> 预警记录
  -> 任务生成与责任人分派
  -> 客户经理跟进
  -> 督办/升级
  -> 完成或复核关闭
  -> 统计、审计和历史归档
```

## 5. 技术栈选型

### 5.1 推荐技术栈总表

| 技术领域 | 推荐方案 | 选型说明 |
|---|---|---|
| 前端框架 | React + TypeScript | 组件生态成熟，适合工作台、表格、权限菜单和复杂表单 |
| 前端构建 | Vite | 启动快、配置简洁，适合管理系统 |
| UI 组件 | Ant Design | 适合后台系统，表格、筛选、弹窗、表单和权限页面较完整 |
| 数据请求 | TanStack Query | 统一处理查询缓存、刷新、加载和错误状态 |
| 图表 | ECharts | 支持风险趋势、任务统计和多维度报表 |
| 后端框架 | Java 17/21 + Spring Boot 3 | 企业级生态成熟，便于接入认证、数据库、任务和监控 |
| 数据访问 | MyBatis-Plus 或 Spring Data JPA | 以公司现有规范为准，复杂查询建议使用 MyBatis |
| 数据库 | PostgreSQL，或公司标准 MySQL | 以公司既有数据库标准、运维能力和合规要求为准 |
| 数据库迁移 | Flyway 或 Liquibase | 保证表结构变更可追踪、可回滚 |
| 定时任务 | Spring Scheduler | 第一阶段足够，降低基础设施依赖 |
| 缓存 | Redis（按需引入） | 用于分布式锁、短期缓存和消息去重，非第一阶段必选 |
| 文件处理 | Apache POI 或 EasyExcel | 支持 Excel 导入、模板校验和错误明细导出 |
| API 文档 | OpenAPI/Swagger | 便于联调和接口维护 |
| 日志监控 | SLF4J/Logback + 可选日志平台 | 支持标准日志输出，并可接入现有日志平台 |
| 测试 | JUnit 5、Mockito、Testcontainers、Playwright | 覆盖后端规则、接口、数据库和关键页面流程 |
| 部署 | Docker Compose、容器平台或标准应用服务器 | 根据项目部署环境选择 |

### 5.2 前端框架选型和理由

推荐使用 React + TypeScript + Vite + Ant Design。

主要理由：

- 系统以后台工作台、数据表格、筛选查询、详情抽屉、任务表单和权限菜单为主，Ant Design 能减少基础组件开发量。
- TypeScript 能提前发现字段名称、接口返回值和表单数据结构错误，适合数据字段较多的业务系统。
- React 组件化方式适合把客户详情、风险标签、任务状态、批次结果和数据源信息拆成可复用模块。
- Vite 开发启动和构建速度较好，便于快速迭代 Demo 到正式系统。
- TanStack Query 可统一处理台账和任务数据的加载、刷新、缓存失效和错误状态，减少页面各自维护请求状态的问题。
- ECharts 适合实现后台所需的风险分布、欠费趋势、任务处理率和逾期统计。

前端不应承担以下职责：

- 不在前端实现最终权限判断。
- 不直接连接数据库。
- 不在页面代码中固化正式预警规则。
- 不将敏感数据写入客户端本地存储、URL 参数或前端日志。

### 5.3 后端是否需要独立服务

需要独立后端服务。

原因：

1. 需要保护客户、欠费、余额和业务状态等内部敏感数据。
2. 需要统一实现角色权限和数据权限，避免仅依靠前端隐藏菜单。
3. 需要执行文件导入、数据预检、批量处理、定时任务和消息发送。
4. 需要保证预警、任务、审计和数据更新在服务端形成一致的业务记录。
5. 需要为前端、AI 服务、数据接入和后续其他客户端提供稳定接口。
6. 需要在服务端控制导出范围、字段脱敏和高风险操作确认。

第一阶段不建议直接采用微服务。采用模块化单体可以保留清晰的模块边界，同时减少服务发现、链路追踪、部署编排和跨服务事务的复杂度。后续当数据接入、通知或统计模块出现独立扩展需求时，再评估拆分为独立服务。

## 6. 后端模块设计

建议后端按领域模块组织，而不是按页面堆叠代码：

| 模块 | 主要职责 |
|---|---|
| identity | 管理账号、登录会话和用户身份 |
| permission | 角色、菜单、功能权限、数据权限和脱敏策略 |
| customer | 客户、客户归属和客户基础信息 |
| business | 专线、业务实例、产品和到期信息 |
| data-ingestion | 文件导入、接口同步、批次、预检和错误明细 |
| ledger | 欠费、余额、到期和处理状态统一台账 |
| risk | 预警规则、风险计算、预警记录和风险状态 |
| task | 任务生成、分派、转派、跟进、关闭和复核 |
| notification | 站内提醒、消息发送、失败重试和发送记录 |
| exception | 数据冲突、缺失、重复、过期和核查记录 |
| report | 统计指标、查询和授权导出 |
| audit | 操作日志、数据变更历史和审计查询 |
| ai-adapter | 对接配置的 AI 服务，提供只读查询上下文 |
| system | 参数配置、字典、规则版本、运行状态和系统管理 |

模块之间建议通过应用服务和领域对象协作，避免页面层直接调用数据库表。预警和任务生成应通过明确的服务接口或领域事件衔接，便于后续替换调度方式。

## 7. 前端技术设计

### 7.1 页面信息架构

建议页面结构：

1. 风险工作台
2. 客户统一台账
3. 任务中心
4. 数据接入与导入批次
5. 数据异常核查
6. 预警规则
7. 统计报表
8. 权限和系统管理

客户经理登录后优先进入风险工作台，直接看到本人负责客户的待办、逾期和高风险事项。后台人员可进入全局工作台，并按区域、客户经理、业务类型和数据批次筛选。

### 7.2 前端状态管理

- 服务端数据使用 TanStack Query 管理。
- 页面临时状态使用 React 状态或轻量状态管理。
- 筛选条件应区分“未提交条件”和“已生效条件”。
- 长列表使用分页、服务端筛选和必要的虚拟滚动，避免一次性加载全部敏感数据。
- 所有异步操作显示加载、成功、失败和重试状态。
- 导入、导出和批量操作显示进度或结果摘要。

### 7.3 关键交互要求

- 风险等级、任务状态和数据异常状态使用统一字典，不在页面中各自定义。
- 客户详情中同时展示业务数据、风险依据、数据来源和处理历史。
- 处理任务时必须明确当前责任人、截止时间、下一步动作和关闭条件。
- 高风险或批量操作要求二次确认，并展示影响范围。
- 数据存在来源冲突时，页面必须显示“待核实”或“存在差异”，不能伪装成确定值。
- 导出操作需要明确筛选条件、数据范围和敏感字段提示。

## 8. 数据架构设计

### 8.1 数据域

建议划分以下数据域：

- **主数据域**：客户、组织、人员、客户经理、产品和业务类型。
- **业务事实域**：余额、欠费、停机状态、专线到期和续签状态。
- **管理过程域**：预警、任务、跟进记录、催办、复核和关闭记录。
- **数据治理域**：导入批次、来源、字段映射、数据异常和修正记录。
- **安全审计域**：登录、查询、导入、导出、分派、规则修改和权限变更日志。

### 8.2 建议核心实体

| 实体 | 关键字段方向 | 说明 |
|---|---|---|
| customer | customer_id、名称、归属组织、客户经理 | 客户主数据 |
| business_instance | business_id、customer_id、产品类型、业务状态 | 客户下的业务或专线 |
| balance_snapshot | customer_id/business_id、余额、快照时间、来源 | 余额快照，不直接覆盖历史 |
| arrear_record | customer_id/business_id、欠费金额、欠费天数、来源批次 | 欠费事实或快照 |
| expiry_record | business_id、到期时间、续签状态、来源批次 | 到期与续签信息 |
| warning | 规则版本、风险等级、触发字段、状态 | 可解释的预警记录 |
| task | 任务类型、责任人、截止时间、状态、来源预警 | 待办和督办主记录 |
| follow_up | task_id、联系时间、结果、备注、附件 | 客户经理跟进过程 |
| import_batch | 来源、文件、批次号、导入人、状态 | 数据接入过程 |
| data_issue | 数据对象、异常类型、责任人、核查结论 | 异常治理记录 |
| audit_log | 操作人、操作时间、对象、动作、结果 | 审计记录 |

### 8.3 数据版本和来源

核心数据不应只保存一个“当前值”。至少需要保留：

- 数据来源系统或文件名称。
- 来源批次号。
- 来源记录标识。
- 获取或导入时间。
- 数据生效时间和业务统计时间。
- 当前是否已核查。
- 是否为系统正式值、人工修正值或待确认值。

对于余额、欠费和状态这类会变化的数据，建议采用快照或事实记录方式保存历史，当前台账由服务端按明确规则计算或选取最新有效记录。

### 8.4 关联和去重

客户与业务关联优先使用公司正式唯一标识。没有唯一标识时，不能仅凭客户名称模糊匹配后直接进入正式台账，应进入待核实队列。

导入去重建议采用：

- 来源系统 + 来源记录编号。
- 业务唯一标识 + 业务统计日期。
- 导入批次和记录哈希作为辅助判断。

重复数据不得静默覆盖，需记录重复类型和最终处理结果。

## 9. 数据接入和处理设计

### 9.1 接入方式

按照优先级建议：

1. 现有业务系统正式接口。
2. 数据交换平台或标准文件交换目录。
3. 标准 Excel 模板人工上传。
4. 其他经批准的人工补录方式。

短信不建议作为正式自动数据源。短信内容可在人工核查场景下作为参考，并保留为核查依据。

### 9.2 导入处理流程

```text
上传文件/接收接口数据
  -> 生成导入批次
  -> 文件和格式校验
  -> 字段类型和必填项校验
  -> 金额、日期、枚举值校验
  -> 客户和业务匹配
  -> 重复和冲突检查
  -> 生成错误明细和预检报告
  -> 人工确认或修正
  -> 写入正式台账
  -> 触发预警计算
```

### 9.3 异常处理

异常至少分为：

- 文件格式错误。
- 必填字段缺失。
- 金额或日期格式错误。
- 客户或业务无法匹配。
- 同一对象多来源冲突。
- 重复导入。
- 数据过期。
- 客户归属缺失或无效。

预检失败时，错误记录应能定位到文件、行号和字段。部分成功时，应明确成功记录和失败记录，不允许用户误认为整批数据已成功。

## 10. 预警和任务调度设计

### 10.1 预警规则

预警规则应包含：

- 规则编号和名称。
- 适用业务类型和客户范围。
- 触发条件及字段。
- 风险等级。
- 处理时限。
- 是否需要人工确认。
- 任务类型和责任人来源。
- 重复触发和解除条件。
- 规则版本和启停状态。

第一阶段可采用规则表 + 服务端规则执行器实现。规则数量和条件复杂度较低时，不建议一开始引入通用规则引擎，以免增加配置和运维成本。

### 10.2 预警计算

建议使用以下组合：

- 数据导入完成后触发一次增量计算。
- 每日或按业务要求执行定时全量校验。
- 支持后台授权人员手工重算指定批次或指定客户。
- 每次计算记录规则版本、计算时间、输入数据版本和结果。

同一客户、同一业务、同一风险事项在有效期内不得重复生成无效预警。数据状态发生变化或原预警已解除时，才允许按规则重新生成。

### 10.3 任务生成和幂等

任务生成应使用业务幂等键，例如：

```text
客户/业务标识 + 预警类型 + 规则版本 + 业务日期
```

任务状态建议包括：

```text
待处理 -> 处理中 -> 待核实 -> 已完成 -> 已关闭
                    └-> 已暂缓
待处理/处理中 -> 已逾期
```

正式状态名称、转换条件和关闭规则由业务负责人确认。

### 10.4 调度实现

第一阶段建议使用 Spring Scheduler：

- 每日导入检查。
- 预警计算。
- 待办生成。
- 临期提醒。
- 逾期识别。
- 消息发送失败重试。

如果后续部署为多实例，定时任务必须增加分布式锁或改用公司统一任务平台。Redis、消息队列或任务调度平台是否引入，以实际并发量、平台标准和稳定性要求评估，不作为第一阶段默认前置条件。

## 11. 接口设计原则

### 11.1 接口分类

- 认证和当前用户信息。
- 客户和台账查询。
- 数据导入、批次和预检结果。
- 预警查询、确认、暂缓和解除。
- 任务查询、分派、转派、跟进和关闭。
- 督办、催办和升级。
- 异常核查和数据修正。
- 统计和授权导出。
- 规则、字典和系统配置。
- 审计和运行状态查询。

### 11.2 接口通用要求

- 使用 HTTPS 和 JSON。
- 统一返回请求标识、业务状态码、提示信息和数据。
- 列表接口支持分页，导出接口采用异步任务或受控的大文件下载。
- 写操作使用幂等键或版本号，防止重复提交。
- 错误信息不能泄露数据库结构、内部路径或敏感数据。
- 服务端根据当前用户重新计算数据权限，不能相信前端提交的范围参数。
- 批量操作返回成功、失败、跳过和待核实数量。

### 11.3 并发控制

任务更新、规则修改、导入批次确认和客户归属变更需要考虑并发。建议使用：

- 记录版本号或更新时间进行乐观锁校验。
- 高风险批量操作使用服务端事务。
- 定时任务使用锁避免多实例重复执行。
- 导入批次状态采用明确状态机，不允许任意回退。

## 12. 权限、安全与审计

### 12.1 认证

第一阶段采用标准账号密码登录，后端负责密码安全存储、登录会话、登录失败限制和退出机制。后续如部署环境已有统一身份认证，可通过认证适配器接入，不改变业务权限模型。

### 12.2 授权模型

采用“RBAC + 数据范围”的组合：

- RBAC 控制菜单、接口和操作类型。
- 数据范围控制客户、区域、部门、客户经理和业务类型。
- 字段级控制联系方式、金额等敏感字段是否完整展示。
- 导出权限独立控制，不能因拥有查询权限自动获得导出权限。

后端每个查询和写操作都必须进行权限校验。前端隐藏按钮只改善体验，不能作为安全边界。

### 12.3 数据保护

- 生产、测试、开发环境隔离。
- 测试使用脱敏或模拟数据。
- 文件上传和下载使用内部存储，并设置权限和有效期。
- 敏感字段按公司标准加密、脱敏或访问控制。
- 导出文件记录导出人、时间、筛选条件、字段范围和文件标识。
- 日志不记录无必要的完整联系方式、账号、金额明细或认证凭据。
- 禁止将真实敏感数据提交到未经项目负责人和安全责任人确认的外部 AI、日志或第三方分析服务。

### 12.4 审计范围

至少审计以下操作：

- 登录、退出和认证失败。
- 客户和台账查询。
- 数据导入、预检确认和批次处理。
- 预警确认、误报、暂缓和解除。
- 任务分派、转派、催办、升级和关闭。
- 规则、权限和系统配置修改。
- 数据修正、批量修改和导出。
- AI 查询请求的用户、时间、查询范围和引用数据版本。

审计日志应支持按人员、时间、对象、动作和结果查询，并按公司制度设置留存周期。

## 13. AI 辅助查询设计

### 13.1 定位

AI 是只读辅助能力，不是账务系统、审批系统或自动执行引擎。

适合支持：

- 查询某客户当前欠费、余额、到期和任务情况。
- 汇总客户经理名下的待办、逾期和高风险客户。
- 解释预警触发依据。
- 汇总指定时间范围内的处理情况。
- 提示数据来源、更新时间和存在的差异。

不允许支持：

- 直接修改欠费、余额、停机或账务状态。
- 直接关闭高风险任务或替代人工复核。
- 通过自然语言绕过数据权限。
- 将不确定数据包装成确定金额、状态或业务结论。

### 13.2 推荐调用链

```text
用户问题
  -> 后端身份和数据权限校验
  -> 识别允许的查询意图
  -> 查询授权范围内的结构化数据
  -> 对数据进行脱敏和最小化处理
  -> 调用配置的 AI 服务
  -> 返回带来源、时间和不确定性说明的回答
```

AI 不应直接连接数据库。后端应先把查询转换为受控的结构化结果，再提供给 AI 生成摘要。

### 13.3 回答要求

- 标明数据更新时间、批次或快照时间。
- 引用客户、业务、预警或任务的必要来源标识。
- 存在数据冲突时明确提示“存在差异”和待核查来源。
- 无法确认时明确说明“当前无法确认”，不得编造。
- 对高风险事项给出建议核查动作，但不直接替代业务人员决策。

## 14. 部署架构和运行环境

### 14.1 推荐部署方式

可部署在开发机、测试服务器、普通云主机、Docker 环境或企业应用服务器中。生产部署应根据项目实际网络和安全要求选择部署方式。

```text
网关/反向代理（可选）
        |
前端静态资源服务
        |
Spring Boot 应用实例（第一阶段可单实例，生产按平台要求部署）
        |
关系型数据库 + 内部文件存储
        |
认证、消息、日志、监控和 AI 服务
```

### 14.2 环境划分

- 开发环境：开发调试，使用模拟或脱敏数据。
- 测试环境：接口、功能、安全和试点前验证。
- 预生产环境：验证部署、配置、数据迁移和性能。
- 生产环境：正式业务数据和受控用户访问。

环境之间不得共享生产账号、密钥和敏感文件。

### 14.3 运行保障

- 数据库定期备份并验证恢复能力。
- 关键任务和接口失败可告警。
- 导入、预警计算和消息发送提供运行状态查询。
- 发布前具备备份和回滚方案。
- 生产配置与代码分离，敏感配置通过公司批准的配置管理方式注入。

## 15. 非功能设计目标

以下为第一阶段建议目标，正式指标需结合试点规模确认：

| 指标 | 建议目标 |
|---|---|
| 可用性 | 满足公司内部系统运行要求，具备故障恢复和人工补处理能力 |
| 普通查询响应 | 常用分页查询在正常负载下不超过 3 秒 |
| 导入反馈 | 小型文件预检在可接受时间内返回；大文件支持异步处理 |
| 数据可追溯 | 核心数据可追溯到来源、批次、更新时间和处理记录 |
| 权限正确性 | 未授权用户无法通过页面、接口或导出获得越权数据 |
| 任务幂等性 | 相同业务事项在规则有效期内不产生重复任务 |
| 审计完整性 | 关键操作均可查询操作人、时间、对象和结果 |
| 可维护性 | 规则、字典、消息模板和权限尽量配置化 |

## 16. 主要风险和应对措施

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 数据来源不统一 | 预警误报、漏报，用户不信任 | 明确正式来源和优先级，保留多来源和核查状态 |
| 客户归属错误 | 任务分派错误 | 使用正式唯一标识，匹配失败进入待核实队列 |
| 欠费或余额口径不清 | 规则计算结果不一致 | 先确认金额、日期、快照和统计口径，再开发规则 |
| 短信不准确 | 错误推动业务动作 | 短信仅作辅助依据，禁止直接触发停机等高风险动作 |
| Excel 数据质量差 | 导入失败或污染台账 | 模板、预检、错误明细、批次确认和回滚 |
| 重复预警和重复任务 | 人员重复处理，降低信任 | 业务幂等键、状态机和解除/重触发规则 |
| 消息发送失败 | 任务提醒遗漏 | 发送记录、失败重试、站内待办和人工补处理 |
| 前端权限不等于数据安全 | 越权查询或导出 | 后端接口强制校验角色、数据范围和字段权限 |
| AI 越权或编造 | 敏感信息泄露、错误判断 | 后端先过滤数据，AI 只读、带来源、无权执行写操作 |
| 过早引入微服务 | 开发、部署和运维成本增加 | 第一阶段采用模块化单体，按实际规模再拆分 |
| 范围持续扩大 | 工期和验收失控 | 明确第一阶段边界，新增内容走变更流程 |
| 缺少真实试点数据 | 无法验证规则和闭环 | 先准备脱敏样例和授权试点数据，设计可复现验收场景 |

## 17. 分阶段实施建议

### 阶段一：需求和平台确认

- 确认正式数据源、数据字段、更新频率和数据责任人。
- 确认客户和业务唯一标识及归属关系。
- 确认预警阈值、任务时限、升级规则和关闭条件。
- 确认认证、消息、日志、文件和 AI 服务的接入方式。
- 完成技术评审和安全评审。

### 阶段二：核心数据和业务闭环

- 完成数据导入、预检、统一台账和异常核查。
- 完成角色权限、数据权限和审计基础能力。
- 完成预警、任务、跟进、催办和关闭闭环。
- 完成后台查询、统计和授权导出。

### 阶段三：试点验证和智能辅助

- 使用脱敏或授权试点数据完成全流程测试。
- 验证预警准确性、任务处理及时性和数据异常处理。
- 根据核心数据和权限稳定性评估 AI 辅助查询。
- 完成试点问题整改和上线验收。

### 阶段四：扩展评估

- 评估合同到期、续签、客户服务事项等扩展场景。
- 评估是否需要消息队列、Redis、独立任务服务或规则引擎。
- 根据规模和效果评估是否拆分服务或接入更多正式数据源。

## 18. 待确认的技术决策

以下问题会直接影响详细设计和实施估算，应在项目启动会或技术评审会上确认：

1. 欠费、余额、停机状态、专线到期和客户归属分别来自哪些正式系统或文件。
2. 各数据源的字段定义、更新频率、数据责任人和接口可用性。
3. 第一阶段采用接口接入、Excel 导入，还是两者并行。
4. 是否已有可复用的认证、权限中心、消息平台、日志平台和文件存储。
5. 项目数据库采用 PostgreSQL、MySQL 还是其他数据库。
6. 项目部署方式、服务器资源、域名和网络访问范围。
7. 余额、欠费金额、欠费天数、到期提前天数等预警阈值。
8. 任务自动分派、人工分派、转派、逾期升级和关闭复核规则。
9. 提醒渠道、模板、发送时间、失败重试和消息留痕要求。
10. 生产数据是否允许进入 AI 服务上下文，是否留存以及留存周期。
11. 首批试点客户经理、区域、客户数量、历史数据周期和验收指标。
12. 正式的系统运维、备份、灾备、日志留存和安全审计要求。

## 19. 方案结论

本项目第一阶段建议采用：

```text
React + TypeScript + Vite + Ant Design
             +
Spring Boot 模块化单体后端
             +
PostgreSQL 或公司标准 MySQL
             +
Spring Scheduler 定时任务
             +
标准登录、消息、日志、文件和 AI 服务
```

该方案能够满足当前欠费、余额、到期、预警、任务和督办的核心闭环，同时保持部署简单、权限集中、数据可追溯和后续扩展空间。开发前最需要优先确认的不是页面技术，而是正式数据源、客户归属、预警口径、任务责任关系和部署环境能力。
